# Feature inventory and release scope

The 46 source page entries and their destinations are listed in `ROUTE_MAP.md`. Thirty-eight historical operational source files are indexed in the private continuity workbench, including the two shared crew entry points. It links their form fields, tables, source hashes, equivalent routes and endpoint references. The private endpoint register distinguishes historical triggers from calls where the export was missing.

| Source feature | Release implementation | Production dependency or difference |
| --- | --- | --- |
| Phumelela and eKaya 2027 capture | Six original route locations, residence switching, NSFAS links, fresh capture after confirmed receipt and stable retry ID | Existing shared spreadsheet and staff GET credential. Verify both operators can capture multiple students on the current backend. |
| Questionnaire dashboard | Access gate, explicit sample, local-residence default, both residence filters, logs and matching KPI counts | eKaya admin markup restored from the matching residence release. Source engine endpoints preserved. |
| Student registration, verification and recovery | `/signup/`, `/verify/`, `/signin/`, `/reset-password/`; verified identity and explicitly assigned residence memberships | Connect Supabase Auth, mail provider and return URLs. Import resident identities separately and issue new verification/recovery links. |
| Resident profile, applications and rooms | Resident profile and assigned bed, application submission, funding document metadata and manager approval/rejection history | Map historical student numbers and account IDs once. A manager provisions a profile and membership. Full historic registration packets and guardian/ID fields require a scoped migration. |
| Physical access, funding and network | The resident can view assigned room, individual financial entries and provisioned network metadata | The old static pass, Wi-Fi password, usage and device figures could be browser-generated. Password toggle/device list are demonstrable with fictional values. Live gate credentials, network telemetry and funding clearance need verified providers. |
| Repair tickets and chat | Student report, maintenance queue, staff acknowledgements, progress, resolution, closure and messages on the same ID | Confirm historical ticket identifiers and an authorised roster before import. The portal displays a saved update. Provider email/WhatsApp delivery requires an acknowledgement connector. |
| Security and visitors | Scoped reports and updates, expected visitors, check-in/out, cancellation, resident visibility | Automatic broadcast, visitor PIN issuance/validation and outbound visitor messages require authorised delivery/access systems. The incident UI identifies a saved report. |
| Transport | Student request, driver queue, acceptance/completion, one-time authorised trip position and ageing timestamp | Legacy GPS sheet, fleet-wide tracking and external dispatch require validated drivers/vehicles. A new trip's position clears on closure. Demos use fixed fictional coordinates without asking for device location. |
| Occupancy and room changes | Bed register, available beds, one active allocation per resident, release and transactional move into an available bed | Import actual bed-level capacity. Moving into a vacant bed is implemented. A simultaneous exchange between two occupied beds needs separate business approval and implementation. |
| Inspections | Schedule, room, date, status and completion in the new register | Historical East/West checklist rows, images, PDF reports and escalation-to-repair links need scoped source adapters. |
| Finance and DULA | Resident-only and management entries, exact decimal ZAR strings and reconciliation status; private eKaya statement review workflow | Review workflow takes extracted text and a residence-scoped roster. PDF ingestion, posting, finance mail and other residence layouts require separate validation. No automated debit/credit posting is enabled. |
| Digital vault and leases | Sample download, optional private PDF/JPEG/PNG upload/download, metadata, MIME/size validation and access rules | Existing Drive folders and signing/evidence need a verified mapping. The blank legacy asset at `/adowa/lease.pdf` names Phumelela and is excluded from signing. |
| Housekeeping and inventory | Requests, queue and closure; scoped stock register with audited receipts/issues and nonnegative quantities | Migrate original units and opening balances. Technician purchasing requests, picture evidence and supplier notifications require integration. |
| Communication and reporting | Published notices visible in student portals, linked resident records, filters, volume chart, current-scope CSV exports | Bulk email, external notifications and analytics across multiple operators require authorised recipient selection and provider delivery confirmation. |
| Exit requests, specialised vetting and laundry | Original routes, requested fields, destination dependencies and migration decisions recorded privately | These specialist workflows remain migration items. Their source systems must remain available during staged adoption. |
| Website and demonstrations | Original visual identity, real homepage enquiry mail draft, marked synthetic residence routes, captioned UI walkthroughs | Demonstration edits stay in this browser and residence. TKC is demo-only because no corresponding operational implementation was supplied. |
